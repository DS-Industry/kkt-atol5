# QR-экраны Telemetron

Экран подключается к Waveshare UART TO ETH (B). В Waveshare нужны TCP Server,
прозрачная передача, UART 2400 8N1, Flow control None и Protocol None. Обычный
TCP-порт экрана в этой установке — 5000. Это не HTTP-порт приложения и не порт ККТ.

## Настройка в админке

Откройте `/admin/displays` или пункт «QR-экраны» в меню.

1. Укажите количество постов самообслуживания, роботов и пылесосов (от 0 до 100
   в каждой группе). Нажмите «Save / Сохранить количество».
2. Появятся отдельные строки: Пост 1, Пост 2, Робот 1, Пылесос 1 и так далее.
3. Заполните IP и TCP-порт каждого экрана. Пустой IP отключает отправку этому
   устройству. Например: Пост 1 — 192.168.28.201:5000; Робот 1 —
   192.168.28.210:5000; Пылесос 1 — 192.168.28.220:5000.
4. Нажмите «Save / Сохранить адреса». Настройки записываются атомарно в
   `instance/config.json`, источник кода не переписывается. Следующая отправка,
   включая ожидающий повтор, использует новый адрес без перезапуска.
5. «Проверить связь» запрашивает info по сохранённому адресу. «Тестовый QR»
   показывает `https://example.com/telemetron-test` и не обращается к ККТ.
   Тест заменяет текущее изображение на экране; проверьте его камерой телефона.

Тестовые кнопки используют сохранённый адрес, а не ещё не сохранённые поля.
Уменьшение количества отключает лишние строки, но сохраняет их адреса для
обратного увеличения. Один IP и порт нельзя назначить нескольким активным
постам, даже если они относятся к разным группам. Разные TCP-порты одного IP
допустимы, если это разные каналы переходника.

## Как определяется экран чека

Существующий запрос `POST /create-check` остаётся прежним: JSON в заголовке Data.

```json
{"name":"2","bay":"1","sum":100,"type":"1"}
```

Поле `name` определяет группу: `"1"` — робот, `"2"` — пост самообслуживания,
остальные значения — пылесос (существующее поведение приложения). `bay` —
номер внутри группы, начиная с 1. Поле `type` по-прежнему отвечает за оплату,
а не выбор экрана. Поэтому Пост 1, Робот 1 и Пылесос 1 — три разные привязки.

После успешного чтения фискального QR и сохранения чека со статусом done
программа добавляет отправку в отдельную таблицу `qr_display_delivery`.
Категория определяется по сохранённому имени чека, которое уже формирует
`create_check`: «Пост N», «Робот N» или «Пылесос N». Отправляется точная строка
QR из результата ККТ, а не заново сформированный чек или картинка.

Отдельная задача APScheduler раз в 3 секунды обрабатывает до пяти отправок.
Она сначала проверяет ответ Telemetron на `info\n`, затем передаёт
`qr=<данные>\n`. Поддерживаются до 200 байт UTF-8 без управляющих символов
и четырёхбайтовых символов. Распознанное эхо команды отмечается как «Принято
экраном»; физическую читаемость подтверждает только сканирование телефоном.

При сетевой ошибке выполняется до трёх попыток с интервалами 5 и 10 секунд
после неудач. Новый чек того же устройства вытесняет старую ожидающую отправку,
чтобы старый QR не заменил более свежий после восстановления связи. История
сохраняет последние 1000 завершённых отправок. В админке показаны последние 20.

Ошибка экрана не меняет done на failed, не запускает повторную фискализацию и
не удерживает блокировку драйвера ККТ. Уже начатая TCP-операция не может быть
перенаправлена задним числом: изменение IP применяется к следующим операциям.
Старые чеки из базы автоматически не отправляются при первом включении функции.

## JSON для интеграции

```http
POST /admin/displays
Content-Type: application/json

{"action":"save_counts","counts":{"wash":2,"robot":1,"vacuum":1}}
```

```http
POST /admin/displays
Content-Type: application/json

{"action":"save_addresses","screens":{"wash":{"1":{"ip":"192.168.28.201","port":5000}}}}
```

Частичное JSON-обновление адресов сохраняет остальные строки. Для чтения:
`GET /admin/displays` с `Accept: application/json`. Для проверки:
`POST /admin/displays/test` с `{"target":"wash:1"}`. Для тестового QR добавьте
`?show_qr=1`. Существующее ограничение доверенной локальной сети для админки
сохраняется.

## Установка обновления

Эти изменения подготовлены на базе ветки `add/ofd-monitoring`, коммит
`95ec58bf74f30237937710afaf06dd2c2f3c13d9`. Рабочий сервис на Orange Pi здесь не
обновлялся. В архив исходников не включены instance, база чеков, секреты и логи.

Перед установкой на действующую кассу сделайте резервную копию проекта,
`instance/`, конфигурации службы и логов. Через имеющиеся `/health` и
`/admin/diagnostics` проверьте кассу; убедитесь, что очередь pending/printing
пуста. Не запускайте второй процесс с доступом к USB-ККТ.

Перенесите исходные файлы с сохранением рабочей папки `instance/`, окружения,
баз данных и настроек. Новых зависимостей нет. После одного штатного перезапуска
службы таблица доставки создаётся через существующий `db.create_all`; данные
фискальных чеков не удаляются. Далее изменения IP в админке не требуют рестарта.
Проверьте здоровье службы, очередь, диагностику ККТ/ФН/ОФД и реальный тестовый QR.

## Проверки разработки

Новые тесты: `python -m pytest tests/test_qr_displays.py`. Они проверяют реальный
локальный TCP-обмен с имитатором, сохранение конфигурации, выбор трёх групп с
одинаковым bay, изменение IP у ожидающей доставки, отбрасывание старых QR и
отсутствие повторной фискализации при ошибке экрана.

На исходной ветке в текущем Windows-окружении воспроизводятся три падения
PNG-тестов: `test_png_exact_payload`, `test_plain_qr_and_card_have_identical_qr_pixels`
и `test_signed_and_latest_routes_render_saved_document`. Они не изменялись в этой
доработке. Аппаратная приёмка интеграции с реальной кассой и дисплеем проводится
отдельно; тесты не создают фискальных документов.
